# 01 · 可行性报告：小米 5s Plus (natrium) 上的 Linux 6.18

> 结论先行：**6.18 内核本身能在这台机器上跑起来**（主线已有完整 natrium 设备树与驱动），
> 但**不能配 LineageOS 的 Android 用户态**。前者是内核移植问题，后者是整个 Android BSP 重写问题。

---

## 一、实测现状（来自你提供的 boot.img，非推测）

文件：`mirrorbits.lineageos.org/full/natrium/20261004/boot.img`
sha256 `1c6fc3896e8949dc9ca78eaf1fe13eba…`，15,163,392 字节

| 项目 | 实测值 |
|---|---|
| boot header | **v0**，page_size 4096 |
| os_version | `0x1e0001a9`（Android 15） |
| kernel_addr / ramdisk_addr / tags_addr | `0x80008000` / `0x81000000` / `0x80000100` |
| cmdline | `androidboot.hardware=qcom ehci-hcd.park=3 lpm_levels.sleep_disabled=1 cma=32M@0-0xffffffff androidboot.boot_devices=soc/624000.ufshc loop.max_part=7` |
| 内核 | `Linux version 4.4.302-perf+`，clang 19.0.1（Android 12701618，含 PGO/BOLT/LTO），构建于 2026-10-04 |
| 内核镜像 | gzip 压缩，28,540,960 字节 → 压缩流 12,922,712 字节 |
| DTB | **不在 header 的 dtb 字段里**，而是以 `Image.gz-dtb` 形式追加在内核之后：尾部 954,557 字节 = **两个 DTB**（475,257 + 479,300，正好填满 `kernel_size`） |
| ramdisk | xz 压缩的 cpio，含 `init`(3.7 MB)、`system/etc/fstab.qcom`、`debug_ramdisk`、`dev` 等 11 项 |

**这组参数就是本工程打包 boot.img 的黄金参照**：header v0、page 4096、地址三件套、追加 DTB 布局、
ramdisk 用 xz —— 全部照抄，只换内核与 ramdisk 内容。

### 追加 DTB 的实测细节（决定打包方式的关键）

解出的两个 DTB 都是**通用 MTP 基树**，不是 natrium 专属设备树：

| | DTB #1 | DTB #2 |
|---|---|---|
| model | `Qualcomm Technologies, Inc. MSM 8996pro + PMI8996 MTP` | `… MSM 8996 v3.0 + PMI8996 MTP` |
| compatible | `qcom,msm8996-mtp`, `qcom,msm8996`, `qcom,mtp` | 同左 |
| `qcom,msm-id` | **`0x131`(305), `0x10000`** | `0xf6`(246), `0x30000` |
| `qcom,board-id` | **`0x2f`(47), `0x0`** | `0x2f`, `0x0` |
| `qcom,pmic-id` | `0x20009, 0x10013` | 同左 |

也就是说：LineageOS 的内核在启动时拿到的是**一棵包含几十种面板配置的通用 MTP 树**（2185 个节点，
`qcom,mdss_dsi_*` 一大串），具体是哪块屏、哪颗触摸芯片，由**下游内核运行时探测**（这正是 DTS 里
`LCD_ID_DET1/2`、`TS_RESOUT_N` 这些引脚名的用途）。

对我们的移植而言这是**好消息**：

1. mainline 的 `msm8996pro-xiaomi-natrium.dts` 声明 `qcom,msm-id = <305 0x10000>`、
   `qcom,board-id = <47 0>` —— **与 bootloader 期待的 `0x131/0x10000` + `0x2f/0x0` 完全一致**，
   所以把我们的 DTB 追加到 `Image.gz` 后面，ABL 会正确选中它。
2. mainline natrium DTS 是**自包含**的（面板 `jdi,fhd-r63452`、触摸 `syna,rmi4-i2c`、
   背光 `pmi8994_wled`、固件路径全部写死在设备树里），不依赖任何运行时探测。
3. LineageOS 的 `fstab.qcom` 里**没有 dtbo 分区**（只有 boot / recovery / cache / userdata /
   system / **cust** / persist / dsp / modem / bluetooth / misc）→ 不存在「ABL 再把 dtbo 叠加层
   套到我们的 DTB 上」的风险，追加 DTB 就是最终生效的设备树。


## 二、6.18 主线对 natrium 的支持核查

在 `torvalds/linux` 标签 **v6.18** 上逐个核对文件是否存在（GitHub API 实测）：

| 硬件 | 主线文件 | 状态 |
|---|---|---|
| 整机设备树 | `arch/arm64/boot/dts/qcom/msm8996pro-xiaomi-natrium.dts` | ✅ 存在（`qcom,msm-id = <305 0x10000>`、`qcom,board-id = <47 0>`，ABL 就是靠这两个值选 DTB） |
| 公共设备树 | `msm8996-xiaomi-common.dtsi`、`msm8996pro.dtsi`、`msm8996.dtsi` | ✅ 存在 |
| 屏幕 | `drivers/gpu/drm/panel/panel-jdi-fhd-r63452.c` | ✅ 存在（natrium 的 `jdi,fhd-r63452`） |
| 显示控制器 + DSI PHY | `drm/msm`、`dsi/phy/dsi_phy_20nm.c` | ✅ 存在 |
| GPU | `drm/msm/adreno/a5xx_gpu.c`（Adreno 530） | ✅ 存在，需 `a530_zap.mbn` 固件 |
| 背光 | `backlight/qcom-wled.c`（PMI8994 WLED） | ✅ 存在 |
| 触摸 | `drivers/input/rmi4/rmi_i2c.c`（Synaptics，DTS 里 `blsp2_i2c6` + GPIO125 中断） | ✅ 存在 |
| WiFi/BT | `drivers/net/wireless/ath/wcn36xx/`（WCNSS/QCA6174） | ✅ 存在，需 `wlan/prima` 固件 |
| 存储 | `scsi/ufs/ufs-qcom.c` + `phy/phy-qcom-ufs.c` | ✅ 存在 |
| USB | `usb/dwc3/dwc3-qcom.c` + `phy-qcom-qusb2` | ✅ 存在 |
| 时钟/PMIC/电源域 | `clk/qcom/gcc-msm8996.c`、`clk-smd-rpm.c`、`qcom-rpmpd`、`spmi-pmic` | ✅ 存在 |
| 远程处理器 | `remoteproc/qcom_q6v5_pas.c`（adsp/slpi/venus）、`qcom_q6v5_mss.c`（modem） | ✅ 存在，需 `mbn` 固件 |
| 音频 | `snd/soc/qcom/`（apq8096 sndcard）+ WCD9335 | ✅ 存在 |
| 摄像头 | `media/platform/qcom/camss/` 存在，但 **natrium 未接线**（DTS 里没有任何 CAMSS/CCI 传感器节点） | ❌ natrium 相机无主线支持 |

`arch/arm64/configs/defconfig`（v6.18）已包含 1812 个符号，其中 `DRM_MSM=m`、`WCN36XX=m`、
`QCOM_Q6V5_PAS=m`、`SCSI_UFS_QCOM=m`、`PINCTRL_MSM8996=y`、`MSM_GCC_8996=y` 等**开箱即有**，
只缺少量符号（面板、fbdev console、rmi4、UFS PHY、F2FS 等），已写入 `build/natrium.config`。

**踩坑记录 1（会让显示直接不亮）**：`DRM_MSM` 的 Kconfig 写着
`depends on QCOM_LLCC || QCOM_LLCC=n`、`QCOM_OCMEM || QCOM_OCMEM=n`、`QCOM_COMMAND_DB || …`、
`QCOM_AOSS_QMP || …`。arm64 defconfig 里 `QCOM_LLCC=m`、`QCOM_OCMEM=m`，于是**即使你写 `DRM_MSM=y`，
它也会被降级成 `m`** —— 而 bring-up 阶段最小 initramfs 里没有模块加载器，`=m` 就等于没有显示。
本工程的 `natrium.config` 已把这些依赖一起设成 `y`/`n`，并在构建脚本里**强制断言** `DRM_MSM=y`。

**踩坑记录 2（不会挡显示，但会挡 3D）**：缺少 `a530_zap.mbn` 时，`a5xx_zap_shader_init()` 的失败
发生在 `a5xx_hw_init()`（**运行时 resume 路径**，见 `a5xx_gpu.c`），不在 probe 路径；
而 `msm_drv.c` 的 `add_gpu_components()` 还有 `of_device_is_available()` 判断。
结论：**没有 GPU 固件也能点亮屏幕跑 fbcon**，只是 GPU 一旦被使用就会失败。


## 三、为什么 LineageOS 用户态 + 6.18 = 走不通

内核换掉之后，Android 的**厂商 HAL 二进制**必须仍然能工作。逐条看它们依赖什么：

| # | Android 侧组件 | 它依赖的内核接口 | mainline 6.18 的替代 | 结果 |
|---|---|---|---|---|
| 1 | `gralloc.msm8996.so` / `libadreno_utils` | `/dev/kgsl-3d0`（下游 MSM kgsl 驱动）+ kgsl ioctl ABI | freedreno + DRM/MSM（完全不同的 UAPI，没有 kgsl 兼容层） | ❌ 开不了 GPU 上下文 |
| 2 | `hwcomposer.msm8996.so`（SurfaceFlinger 必需） | `mdss_fb` / `/dev/graphics/fb0` + msm fb ioctl | DRM/KMS（无 fb 兼容 ioctl） | ❌ 无 HWC → 无画面 |
| 3 | `/vendor/lib/modules/wlan.ko`（qcacld-2.0）、`btwilink` 等 | 4.4 内核内部符号 + vermagic `4.4.302-perf+` | 主线用 `wcn36xx` 驱动（完全不同的驱动模型） | ❌ 模块无法加载，且 qcacld-2.0 无法移植到 6.18 内核 API |
| 4 | 图形内存分配 | `/dev/ion` + 厂商 ioctl | dma-buf heaps（`/dev/dma_heap/*`） | ❌ 分配器 ABI 不同 |
| 5 | `libril-qc-qmi-1.so` + `qcrilmsgtunnel`（通话/短信/数据） | `/dev/smd*`（下游 `smd_pkt`）、`/dev/qmi` | rpmsg/glink/qrtr（不同设备节点与协议栈） | ❌ rild 起不来 → 无信号 |
| 6 | `camera.msm8996.so` | 下游 msm camera (`/dev/video*` 厂商 ioctl) | CAMSS（natrium 未接线） | ❌ 相机无解 |
| 7 | SELinux 策略 `/vendor/etc/selinux` | 引用大量下游节点（`sysfs_kgsl`、`mdss_fb`…） | 主线没有这些节点 | ❌ 策略编译/avc 直接拒 |

再加上你的内核带的是**高通下游补丁集**（`lpm_levels`、`ehci-hcd.park`、`cma=32M@0-0xffffffff` 等），
Android 15 的 vendor 分区就是围绕这套接口构建的。

**一句话**：这不是「换个内核」的事，而是要把 HWC、gralloc、RIL、相机 HAL 全部重写成基于
DRM/dma-buf-heaps/rpmsg 的实现，外加把 qcacld-2.0 移植到 6.18。msm8996 上业界至今没有
「mainline + Android 用户态」的成功案例，原因就在这里。

### 你可以自己验证（不用信我）

把手机连上电脑（开启 USB 调试），跑 `tools/collect-android-evidence.sh`，
或在手机上用 root shell 直接看：

```sh
ls -l /dev/kgsl-3d0 /dev/ion /dev/graphics/fb0        # Android 图形栈的命门
ls /dev/smd*                                          # 通话走的下游节点
modinfo /vendor/lib/modules/wlan.ko | grep vermagic   # 应为 4.4.302-perf+
uname -r                                              # 4.4.302-perf+
ls /vendor/lib/hw/ | grep -E 'gralloc|hwcomposer'     # 厂商 HAL 二进制
```

只要 `/dev/kgsl-3d0` 在、`hwcomposer.msm8996.so` 在，就说明 Android 图形栈离不开下游内核。

## 四、可行路线

### A. 最小 bring-up（本次先交付）
只装一个最小的 initramfs：内核起来 → 屏幕显示 `dmesg`（`fbcon`）→ 背光拉满 →
USB 配置成 ACM 串口，电脑上 `screen /dev/ttyACM0 115200` 就能进 shell。
**得到**：证明 6.18、DTB、面板、UFS、USB 都活着。
**风险**：几乎没有（可 `fastboot boot` 临时启动，不写 flash）。

### B. postmarketOS / Alpine（推荐的真实系统）
主线设备支持已在 pmOS 存在（`device-xiaomi-natrium`、`firmware-xiaomi-natrium` 包），
用本次编译的 6.18 + 模块替换其内核即可。
**得到**：显示、触摸、WiFi、蓝牙、GPU、音频、USB 网络共享，桌面环境（Phosh/Plasma Mobile）。
**失去**：相机（主线无驱动）；modem/通话需要额外固件与 q6voiced 配置，属于「可能能搞」而非「开箱可用」。

### C. 想继续用 Android 应用 → pmOS + Waydroid
Waydroid 在 Linux 上用容器跑 Android，依赖 binder（主线 6.18 有 `ANDROID_BINDER_IPC`/`binderfs`）
与 GBM/DRM 图形（freedreno 支持 Adreno 530）。**这是 6.18 上唯一能碰到 Android 应用的路**，
但它不是完整手机系统：没有通话、没有相机，性能受限于容器与主线 GPU 驱动。

### D. 另一个方向：不追 6.18，保留 4.4 做特性回移
如果目标只是「手机更好用」，把 mainline 的某些驱动/修复回移到 4.4 上游化分支，
收益远大于把 6.18 塞进 Android。**这条路的产出是改进的 LineageOS 内核，不是 6.18。**
