# 04 · 能不能拿 OTA 包「改成适配 6.18」？

你给的包：`lineage-22.2-20261004-nightly-natrium-signed.zip`
（995,123,443 字节，sha256 `8c40047299c800738c1f22f206799167cf55c08aaa0a0ac4af8bfebbb7f65fe9`，与 LineageOS 官方 API 公布值**一致** ✅，Android 15 / SDK 35）

**直接回答：不能。** 但不是因为"包不完整"，而是因为包里真正决定能否启动的东西是**编译好的厂商二进制**，
它们从编译期就绑死在 4.4 下游内核的私有接口上；改 zip 只能改字节，改不了 ABI。

---

## 一、这个包里到底有什么（实测清单）

解开 zip 后只有 15 个条目，关键的是：

| 文件 | 大小 | 说明 |
|---|---|---|
| `system.new.dat.br` | 827,334,774 B | system 分区（block-based OTA 的 brotli 压缩块） |
| `vendor.new.dat.br` | 130,904,823 B | **vendor 分区 —— 厂商 HAL 与内核模块就在这里** |
| `boot.img` | 15,163,392 B | 内核 + ramdisk（与我们分析过的那份一致） |
| `recovery.img` | 22,290,432 B | recovery |
| `system.transfer.list` / `vendor.transfer.list` | — | 块映射表（还原镜像用） |
| `META-INF/com/google/android/updater-script` | 1,597 B | OTA 刷写脚本 |

**注意：包里没有 `dtbo.img`** —— 与我们从 fstab 得到的结论一致：natrium 没有 dtbo 分区，
设备树就是 boot.img 里追加的那一份。这对我们的 6.18 打包是有利条件（不存在 dtbo 叠加层干扰）。

## 二、为什么「改 zip」改不动（以下全部是对你这个包的实测）

把 `vendor.new.dat.br` 还原成 ext4 后（832 MB 文件系统，全部 212,992 个块），
vendor 分区里的厂商 HAL 是这些（32 位 + 64 位两套，都在 `/lib/hw`、`/lib64/hw`）：

| 厂商二进制 | 大小（arm / arm64） | `strings` 里对下游内核接口的引用 |
|---|---|---|
| `hwcomposer.qcom.so` | 202,992 / 283,360 B | SurfaceFlinger 必需，走厂商显示接口 |
| `gralloc.msm8996.so` | 44,184 / 64,776 B | **`/dev/ion` ×5** |
| `gralloc.default.so` | 11,764 / 23,760 B | `mdss_fb` ×1 |
| `android.hardware.graphics.mapper@2.0-impl.so` | 19,884 / 31,816 B | 图形映射 HAL |
| `camera.msm8996.so` | 334,500 B | `/dev/ion` ×1 |
| `android.hardware.camera.provider@2.4-service` | 5,924 B | 相机 provider |
| `vendor.qti.hardware.memtrack-service` | 23,568 B | memtrack |
| `audio.primary.msm8996.so` | 375,628 B | `mdss_fb` ×1 |
| `android.hardware.bluetooth@1.0-impl-qti.so` | — | `/dev/smd` ×2 |
| `fingerprint.fpc.so` | — | `/dev/ion` ×4 |

（这些都是 **ELF 二进制**：`.so` 是编译产物，源码不在 AOSP 里；改 zip 只能改字节，改不了它们要的 ioctl。）

### 全量扫描结果（vendor 分区 1062 个 `.so` 逐个统计）

| 下游接口 | 引用的库数 | 总引用次数 | 最主要的几个 |
|---|---|---|---|
| **`kgsl`**（`/dev/kgsl-3d0`，Adreno 私有驱动接口） | 5 | **178** | **`libgsl.so` 167 次**、`libqti-perfd.so` 5、`libadreno_utils.so` 4 |
| **`/dev/ion`**（下游图形内存分配器） | 26 | **59** | `gralloc.msm8996.so` 5、`libadsprpc.so` 5、`libmmcamera2_pp_buf_mgr.so` 5 |
| `mdss_fb`（下游显示帧缓冲） | 4 | 4 | `gralloc.default.so`、`libsdmcore.so`、`libsdmextension.so`、`libmmcamera2_mct.so` |
| `/dev/smd*`（下游 SMD 通道，通话/蓝牙） | 1 | 2 | `android.hardware.bluetooth@1.0-impl-qti.so` |

**合计 35 个厂商库直接依赖 4.4 内核的私有接口。** 原始数据在
[lineage-ota/analysis/09-vendor-libs-abi.txt](lineage-ota/analysis/09-vendor-libs-abi.txt)
（HAL 清单在 `03-vendor-hal.txt`，分区结构在 `07-vendor-tree.txt`）。

这就是"改 zip 改不动"的量化答案：你要替换的不是几个文件，而是 35 个**没有源码**的二进制库
所依赖的那一层内核 ABI。

| Android 组件 | 它要求内核提供 | 6.18 主线提供 | 换 zip 能否解决 |
|---|---|---|---|
| `hwcomposer.qcom.so`（SurfaceFlinger 必需） | `mdss_fb` / `/dev/graphics/fb0` 的厂商 ioctl | DRM/KMS（完全不同 UAPI） | ❌ 二进制，源码不在 AOSP |
| `gralloc.msm8996.so`、`libgsl.so` | `/dev/kgsl-3d0` + `/dev/ion` | freedreno + DRM + dma-buf heaps（无 kgsl/ion 兼容层） | ❌ 同上 |
| `/system/lib/modules/*.ko`（qcacld-2.0 等） | 4.4 内核内部符号 + vermagic | 主线用 wcn36xx | ❌ 见下节实测 vermagic |
| `libril-qc-qmi-1.so`、`qcrilmsgtunnel` | `/dev/smd*`（下游 smd_pkt） | rpmsg/glink/qrtr | ❌ 无对应节点 |
| `camera.msm8996.so` | 下游 msm camera 驱动 | natrium 主线**根本没有** CAMSS 节点 | ❌ 无解 |
| SELinux 策略 | 引用 kgsl/mdss_fb 等节点 | 主线无这些节点 | ❌ 策略要重写 |

**把 6.18 的 boot.img 刷进这个系统会怎样**：内核能起来、显示驱动能初始化，
但 Android init 拉起的 `hwcomposer.qcom.so` 打不开 `/dev/kgsl-3d0` 与 `mdss_fb`，
SurfaceFlinger 起不来 → **黑屏 / 循环重启**。这不是"少打一个补丁"，是整套 HAL 的接口对不上。

### 额外实测：这个 ROM 里连一个可加载模块都没有

我把两个镜像都还原出来逐个目录找过 `.ko`：

| 镜像 | 大小 | `.ko` 数量 |
|---|---|---|
| vendor（cust） | 832 MB 文件系统（212,992 块） | **0** |
| system | 3,072 MB 文件系统（786,432 块），`/lib/modules` 不存在 | **0** |

也就是说：WiFi（qcacld-2.0）、触摸、显示等驱动**全部编译进了 4.4 内核镜像内部**，
Android 侧根本没有"换个 .ko 就能换驱动"的余地。而且 Android 的 WiFi 栈走的是 qcacld 私有 ioctl
（配套的 `libwifi-hal-qcacld.so` / 厂商 supplicant），主线的 `wcn36xx` 是标准 mac80211/cfg80211 驱动，
**接口层面也对不上** —— 这比"模块 vermagic 不匹配"更彻底。

## 三、唯一理论可行的路线（以及它的真实规模）

要让「Android 用户态 + 主线内核」成立，需要做的是**重做 device tree / HAL 层**，而不是改 zip：

1. **图形分配器**：gralloc 换成 minigbm（GBM/DRM 后端）
2. **合成器**：HWC 换成 `drm_hwcomposer`（AOSP 生态里为 DRM/KMS 写的 HWC 实现，Chromebook/Android-on-mainline 在用）
3. **GPU**：Mesa freedreno（主线 Adreno 530 驱动）+ 固件 `a530_zap.mbn`、`a530_pfp.fw`、`a530_pm4.fw`
4. **内存**：dma-buf heaps（Android 15 原生支持，这块反而好办）
5. **通信/通话**：没有现成方案。需要基于 qrtr/rmnet 重写 RIL 通路；而 msm8996 的主线 modem 支持本身
   也只到「能起来」的程度，离 Android Telephony 可用还差很远
6. **相机**：**直接放弃**（主线无驱动）
7. **SELinux**：整份 vendor 策略重写
8. **Android 侧**：kernel headers、init.rc、模块加载、ABI 全部对齐

> 结论：这是「为一颗已经 EOL 的 SoC 重新实现一遍 Android 平台」，
> 工作量以**人月起算**，而且关键前提（厂商 HAL 源码）并不公开 —— 厂商只发布二进制。
> 业界至今没有 msm8996 + mainline + Android 用户态的成功案例，原因就在这里。

## 四、那这个 OTA 包对你到底有什么用

它非常有价值，但价值不在"改成 6.18"：

1. **回滚保险**：里面的 `boot.img` 就是你的原厂内核（已存 [bootimg/lineage-boot.img](bootimg/lineage-boot.img)，
   sha256 `1c6fc389…`）。刷了 6.18 之后一条 `fastboot flash boot` 就能回去。
2. **固件来源**：`vendor` 分区里有 GPU/modem/adsp/slpi/venus 固件与 wlan 固件，
   是 6.18 跑真实系统（路线 B）必须的燃料。
3. **取证依据**：本文档的结论全部建立在对**你自己这个包**的实测之上，不是我空口断言。
4. **对照基准**：pmOS 用同一份固件、同一块硬件跑主线内核 —— 证明"硬件没问题，是 Android HAL 绑死了内核"。

## 五、如果你要的是「Android 应用 + 6.18」

唯一现实的组合是：**6.18 + postmarketOS + Waydroid**。
Waydroid 在 Linux 上以容器方式跑 Android，用的是主线内核的 binder/binderfs（6.18 已有）
与 freedreno 图形栈，不需要 kgsl/mdss_fb 那套厂商接口。

代价：它是**容器化 Android**，没有通话、没有相机，性能取决于主线 GPU 驱动。

详见 [03-postmarketOS接入.md](03-postmarketOS接入.md)。
